# 安全の教訓

以下はすべて、このプロジェクトで実際に起きたことです。共通点は、このスマホの Windows には自前の電力管理も熱管理もなく、スマホにも PC にも気づかれない形で止まりうることです。無人で回す前に、安全装置を作っておく必要があります。English: [../safety-lessons.md](../safety-lessons.md)

## 1. 固まった Windows が電池を過熱させた(2026-10-27)

Windows が固まり(BSOD ではなく画面停止)、約 10 時間放置されました。筐体は非常に熱くなり、電池は両セルとも膨らみました。原因は設計にありました。MuChain は、Windows が起動する時間を稼ぐために、`ExitBootServices` で Gunyah のウォッチドッグを止めます。Windows には熱制御がなく(プロセッサーの電力管理が読み込めない)、`run.cmd` の「40 分後に再起動」という保険は、Windows が生きていないと動きません。

置き換えた仕組み(`drivers/dbgcap`):

* **ウォッチドッグの維持。** MuChain がウォッチドッグを動いたまま Windows に渡します。`dbgcap` が読み込まれると、ウォッチドッグを再び有効にして 1 秒ごとに ping します。ただし、全 CPU で 500 ms のタイマー DPC が動き、温度が許容範囲のときだけです。Windows が止まれば ping も止まり、約 30 秒後にスマホがリセットされます。ping はカーネルからの `smc #0` が必要です(HVC ではウォッチドッグに届きません)。小さな `armasm64` のスタブです(`drivers/dbgcap/smc.asm`)。
* **電池温度での停止。** 電池温度(ACPI の電池と同じ RAM ブロックから)を 1 秒ごとに読みます。40℃ を超えると性能の予算を絞り、48℃ が 10 秒続くと ping を止めて、スマホを Android に再起動します。
* **ソフトウェアの CPU ガバナー。** 電力管理(PPM)がないため、`dbgcap` が 100 ms ごとに負荷を読み、EPSS の性能状態を自分で設定します。その上に熱の予算をかけています。

この保護は、`run.cmd` が `dbgcap` を開始した後にだけ効きます。起動の初期と「掃除用」の起動は無防備です。無人で動かす前に、固まった状態が本当にリセットで終わることを確認してください。

## 2. Windows Update で起動不能になった(2026-10-19)

USB ネットワーク経由で Windows Update が OS を入れ替えました(28000.1 から新しいビルドへ)。カーネル、ローダー、コード整合性ポリシー、約 3700 ファイルです。次の再起動から、起動しなくなりました。このスマホのローダーは古いファイルなら受け付けますが、新しいファイルは拒否します(新しい `winload` はコード整合性ポリシーを要求し、この環境はそれを読み込みません。システムハイブの作り直しも必要でした)。

復旧: Windows のパーティションを PC に取り込み、WinSxS に残っているコピーでファイルを巻き戻し、変わったチャンクだけを書き戻しました。そのあと、更新が戻ってこないようにしました。`WinSxS\pending.xml` を退避し、更新サービスと `TrustedInstaller` を無効にし、更新ポリシーを設定します(`tools/windows-image/neutralize_update.py`、`disable_wu_offline.py`)。

得た教訓: 最初に動かす前に基準イメージを保存します。Windows を動かして中身が変わったら、新しく取り直します。古い基準に対する差分を書き込むと、NTFS が不整合になります。Windows にインターネットを与えるものは、何でも更新を勝手に起動しえます。

## 3. その他

* **全 LUN の GPT 書き換え:** [gpt-incident.md](gpt-incident.md)
* **debugfs でのレジスタダンプは SoC を固めます**(Sahara のメモリデバッグモードに入る。PCIe の `phy` ベースを読むとカーネルパニック)。戻すには、PC から Sahara リセットを送ります(`tools/pc-link/sahara_reset.ps1`)。ダンプは 1 ブロックずつ行ってください。
* **すでに存在するデバイスにドライバーを入れると、即座にバインドされます。** WLAN ドライバーへの `pnputil /add-driver ... /install` で Windows が固まりました。割り込みが届かないチップに対してドライバーが動き出したためです。先にエンドポイントを無効にし、`Start=4` で導入してください。ユーザーランドの前にマシンが死んだ場合は、イメージの SYSTEM ハイブで、サービスの `Start` を外から 4 に戻します(`host-scripts/offline_fix.ps1`)。
* **レジストリキーへの `New-Item -Force` は、キーの値を消します。** WLAN サービスの `ImagePath` が消え、デバイスがレジストリの問題を示しました。
* **PowerShell の `0x7FFFFFFF` を超える 16 進リテラルは、負の `Int32` です。** `0x8F002820` のような IOCTL コードが `uint` への変換で失敗し、例外が握りつぶされ、ドライバーのバグを探して 6 サイクルを無駄にしました。こうした値は `[Convert]::ToUInt32('8F002820', 16)` で作り、例外はログに出してください。
* **Windows 自身の再起動は Android に戻ります。** 本当の電源オフはありません。Windows のシャットダウンは、充電画面になるか、長押しが必要になります。ランチャーは、どんな終わり方でも Android への再起動として扱います。
* **Windows から ITS を変更するコマンドを送らないでください**([wifi-bringup.md](wifi-bringup.md))。また、未確認の物理アドレスを読まないでください。どちらもマシンが止まります。起動時開始のドライバーにディスクへ書き込ませないでください(起動の初期にハングしました)。ETW のトレースは循環ファイルに書いてください。ESP の普通のトレースファイルは、マシンが止まったときに壊れました。
* **fastboot が列挙されないのは、USB ポートが悪かったためで、ケーブルではありませんでした。** ポートを替えて直りました。
* **`esp_put.ps1` は、バックスラッシュが二重のパスを渡すと、黙って空のファイルを書くことがあります。** ESP に書いた後は、必ずサイズを確認してください。

## 4. まだ未解決のこと(2026-11-02)

26100 ゲストで Wi-Fi を上げたままのウォッチドッグ試験(わざと ping を止めてリセットを待つ)で、スマホが Android に戻りませんでした。EDL のデバイス(`19D2:0112`、USB 名 `QUSB_BULK_CID:0448_SN:...`。Qualcomm のシリアルドライバーがないとエラー表示になり、別の機器と見間違えやすい)として現れ、その後は USB に応答しなくなりました。以前の同じ種類の試験では復帰しています。そのときは WLAN リンクなしだったと思われますが、推測です。原因は分かっていません。分かるまでは、「ガードが固まった Windows をリセットする」ことは以前の構成でだけ確認済みと考え、Wi-Fi を上げたままの無人運転はしないでください。
