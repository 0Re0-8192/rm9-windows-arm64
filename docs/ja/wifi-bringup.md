# Wi-Fi の立ち上げ: スマホ SoC の WCN7850 を Windows で動かす

このスマホの WLAN チップ(Qualcomm WCN7850 / FastConnect 7800、PCI `17cb:1107`)は PCIe0 につながっています。Android ではカーネルと CNSS ドライバーが立ち上げます。Windows にはこのチップ用のドライバー(X Elite のノート PC 向け)がありますが、SoC 側を立ち上げるものはありません。「リンクがない」から「接続して、アドレスを取り、ping が通る」までの道を、問題が出た順に書きます。各ステップは、Android の動きとの比較か、失敗する段階を原因が 1 つになるまで切り詰める方法で見つけました。English: [../wifi-bringup.md](../wifi-bringup.md)

日付は 2026-10 です。レジスタの値は、この SM8650 の基板のものです。

## 1. Android が何をしているか調べる

Android のカーネルには `CONFIG_TRACE_MMIO_ACCESS` があります。ftrace で `events/rwmmio` を有効にして WLAN モジュールを外し、入れ直すと、CNSS がチップの電源を切って入れ直し、リンク有効化の手順が丸ごとトレースに残ります(`tools/android-trace/android_trace_pcie3.sh`、`mmio_window.py`、`mmio_pre.py`、`mmio_filter.py` で絞り込み)。

そこから順序が分かりました。GPIO(WLAN_EN、PERST#、CLKREQ#、WAKE)、RPMh の電源、PARF レジスタ、114 エントリの PHY テーブル、PHY の準備完了から約 12 ms 後の PERST# 解除、DesignWare の DBI 設定(1 レーン、イコライズ)、最後に LTSSM の有効化です。リンクはその約 16 ms 後に確立します。PHY テーブルはデバイスツリー(`qcom,phy-sequence`)にあり、`tools/uefi-patch/gen_pcie_physeq.py` が `src/muchain/pcie_physeq.h` に変換します。

動作中のスマホでやるときに、避けることが 2 つあります。PCIe レジスタ空間の debugfs ダンプ(`pci-msm`)は、SoC を Sahara のメモリデバッグ(ダンプ)モードに落とすことがあります。`phy` ベースを読むとカーネルパニックです。ダンプモードから戻すには `tools/pc-link/sahara_reset.ps1` を使います。

## 2. 訓練されないリンク

手順を UEFI で再現すると、PHY は準備完了になり、ルートコンプレックスも読めました。ところが LTSSM が `DETECT_QUIET` と `DETECT_ACT` を行き来し続けました。受信器が検出されません。電源、クロック、スリープクロック(PMK8550 の GPIO を代替機能のクロック出力に設定)は、すべて Android と同じでした。

足りなかったのは、TLMM のレジスタ 2 つでした。WLAN_EN を有効にする前に、Android は GPIO18 と GPIO19 の `INTR_CFG` レジスタに `0x7c2` を書きます(CNSS のデバイスツリーのノードの `mpm_wake_set_gpios`)。WAKE の線の GPIO96 にも同じ値です。これで、チップの SW_CTRL が MPM/PDC につながり、AOP を介して、チップの電源が動作電圧まで上がります。これがないと、チップは半分しか給電されず、見えません。書くと、Gen1 x2 のリンクになり、エンドポイント ID は `0x110717CB` でした。

約 1 週間かかった理由: 比較を、誰もが知る GPIO(16、94、95、96)に限っていたからです。電源投入の窓にある TLMM への書き込みを、TLMM 全体で差分したことがありませんでした。**予想したアドレスではなく、窓の中のすべてのアドレスを差分すること。**

## 3. Windows が PCI デバイスを見る

Windows が PCI を列挙するには ECAM が必要です。DesignWare の iATU を CFG shift モードにすると、`0x60100000` のバス 1 の窓を ECAM 領域として使えます(デバイス 0 が応答し、ほかは UR を返す)。ACPI 側は、`PCI0` ホストブリッジ(`PNP0A08`、ルートバス 1)と MCFG テーブルです。ここで時間を取られた点が 2 つあります。MCFG のベースは「バス 0 の位置」(`0x60000000`)で、開始バスを 1 にすること。もう 1 つは、`PCI0` を含む DSDT は、リンクの訓練を済ませたファームウェアとだけ組み合わせて起動することです。そうしないと、Windows が初期化されていない ECAM を読んで止まります。

これで Windows は `PCI\VEN_17CB&DEV_1107` を列挙します。

## 4. MSI: 1 週間以上止まった所

ドライバー(`qcwlanhmt8380`)はバインドされます。そのあと、Windows の HAL が GIC ITS 経由で MSI を設定し、マシンが `CLOCK_WATCHDOG_TIMEOUT` で死にます。ITS が止まり(`GITS_CREADR` が進まなくなる)、ある CPU がそれを永久に待つためです。このスマホは Gunyah ハイパーバイザーのゲストとして Windows を動かしていて、GIC と ITS を仮想化しています。Windows から、テーブルを変える ITS コマンド(MAPD、MAPC、MAPTI、DISCARD)を送ると、マシンが止まります。送らないでください。

## 5. まずポーリングで、チップが動くところまで

ドライバーに割り込みが届かないので、代わりにカーネルドライバーから、ドライバー自身の割り込みハンドラーを呼びました。PASSIVE_LEVEL のワークアイテムが、MHI コントローラーとコピーエンジンのハンドラーを数ミリ秒ごとに呼びます(DISPATCH_LEVEL の DPC だと、ドライバーの待機がデッドロックします)。ハンドラーを公開するために、ドライバーに 2 か所の小さなパッチが必要でした。ワークアイテムは `drivers/dbgcap` にあります。結果として、SBL、BHIe、AMSS、QMI/WLFW、`FW_INIT_DONE`、HTC、WMI が立ち上がり、スキャンで周囲の 20 個のネットワークが見えました。

次に、接続が特有の形で失敗しました。接続は確立し、約 7 秒後に Windows が止まります。パケットのトレース(ETW を `tracerpt` で CSV に)では、アクセスポイントからの EAPOL がなく、そのあと Deauth が来ていました。ポーリングの対象は MHI とコピーエンジンだけで、データ経路を担う **ext-group**(受信の REO と、送信完了)が入っていませんでした。そのため 4-way ハンドシェイクが届かず、AP が諦め、その後始末で Windows が止まっていました。ext-group のハンドラーも呼ぶようにすると(`drivers/dbgcap` の `DpPoll`)、接続、DHCP、`ping 8.8.8.8` が通りました。ポーリングを PASSIVE_LEVEL で回すことで、切断時の停止もなくなりました。

## 6. 再起動で固まる問題

Windows は、ルートポート自身の MSI を ITS に登録します(DeviceID `0x1301`)。ノードを停止・削除するとき、または再起動のとき、そのデバイスに `MAPD` を V=0 で送り、ハイパーバイザーは「未実装」と返します。ハイパーバイザーにとってルートポートは仮想デバイスで、物理なのはエンドポイント(`0x1401`)だけだからです。ITS が止まり、Gunyah も一緒に止まります。これが、長く続いた 2 つの症状の正体でした。前回の古い PCI ノードが残る起動が約 170 秒でハングすること。シャットダウン時にノードを消そうとするとマシンが固まること(初期の構成で、本番の起動のたびに捨て駒の「掃除用」起動を挟んでいたのはこのためです)。

回避策は、ルートポートを MSI から外すことです。`Interrupt Pin` を 1 にして(DBI のオフセット `0x3C`。読み取り専用の項目は、`0x8BC` の `MISC_CONTROL_1` のビット 0 で解除)、Windows に `_PRT` 経由で INTx を使わせ、ルートポートの MSI を登録させません。MuChain が Windows の起動前にこれを行い、`guest/rpfix.ps1` は動作中に行えます。これで掃除用の起動は不要になりました。

## 7. 本物の割り込み

チップの MSI の宛先は、ITS 以外にできます。GIC にはメッセージベース割り込み(MBI)のフレームがあります。チップの MSI のアドレスを `0x17110040` の MBI フレームにし、データを `800 + ベクタ` にすると、割り込みは VM に普通の **SPI**(800〜811)として届きます。あとは、Windows にその SPI を教える必要があります。ルートから列挙したデバイスは、ARM64 ではリソースが正しく翻訳されません(`IRQConfig` が `STATUS_NOT_FOUND` で失敗)。そこで DSDT に本物の ACPI デバイス `RM9I0001` を足し、`_CRS` でエッジ割り込み 800〜811 を宣言します(`tools/acpi/add_irq.py`)。小さなドライバー(`drivers/rm9irq`)がこれにバインドし、12 本すべてを `IoConnectInterruptEx` で接続します。ISR は名前付きイベントを通知し、`dbgcap` のカーネルスレッドがそれを待って、ポーリングのときと同じ処理を、時間ではなくイベントで実行します。周期のポーリングは、遅い保険として残します。

実測: 起動の最初からパケットロスなし。キックの設定が 5 ms / 30 ms で約 45 Mbit/s(調整した実行では 80〜97 Mbit/s に達したが、CPU の起床がずっと多くなる)。アイドルでは 1 秒に約 66 回の起床です。これは本番の `run.cmd`(`guest/esp_run_prod_wifi.cmd`、常駐モードの `guest/rpfix.ps1`)に統合されています。

## ITS 経路そのものがまだ動かない理由

デバイス側の LPI は、ここではゲストに届きません。デバイス ID の候補と Android 風の IOVA で、SMMU を通す試験をしましたが、成功しませんでした。テーブルの状態、WFI、IAR の挙動は、それぞれ原因から除外しています。このリポジトリは、原因を説明するのではなく、回避しています。調査を続けるなら、Gunyah のソースが手がかりです。

## 一般化できる教訓

* 疑ったアドレスだけでなく、動いている系のすべてのアドレスと突き合わせる。
* 動いている系自身の手順を(MMIO のトレースで)記録する。ソースから再構成しない。
* ハイパーバイザーの、仮想デバイスに対する「未実装」は、ずっと後の後始末の時に、ハングとして現れることがある。
* 割り込みに依存する段階では、ポーリングが最初の一歩として有効。「チップが動く」と「割り込み経路が動く」を切り分けられる。ただし、ポーリングの対象が全部であることを確認すること(データ経路の ext-group が不具合でした)。
